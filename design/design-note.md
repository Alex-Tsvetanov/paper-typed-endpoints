# P5 design note (DRAFT, not frozen)

Status: draft of 2026-10-23. Nothing here is frozen. No hypotheses file exists yet. No laptop
hour is computed: the estimates below give their formula and say where the measured basis will
come from. This note replaces the assumptions of plan v2 section 3.2 (10 sizes x 2 generators,
8 comparisons, 30 s per compile) with a design; the numbers of runs follow from it, the times do
not yet.

## 1. Question and delta over ctpb

Claim (brief): C++26 static reflection generates unary protobuf endpoints without `protoc`. The
paper measures compile time against schema size, end-to-end unary calls against
`protoc`-generated code, and interoperability with grpc-go. Unary only.

ctpb (TELECOM 2026) is the conference artifact. Its camera-ready errata (Alex's open item) list
claims the code did not back. P5 does not edit ctpb; it makes those claims measured or tested in
its own implementation:

| ctpb erratum | What P5 does instead |
|---|---|
| E1 `#embed` never used | The tests and the compile-curve programs read the `.proto` file with `#embed` (GCC 16 accepts it in C++26 mode). |
| E2 the P2996 path never compiled; a silent C++20 fallback was measured | `tep/reflect.hpp` has a hard `#error` without `__cpp_impl_reflection`; a compile-fail test checks it; `static_assert`s check by reflection that the synthesized members match the schema. |
| E3, E9 members did not match every field; fixed-width types went out as varints | Every proto3 scalar, enums, nested messages and repeated fields are synthesized. The encoder's output equals `protoc`'s encoding byte for byte for all 15 scalar types. Maps and oneofs are refused with a compile-time diagnostic. |
| E7 schema errors were silently accepted | Every schema error is a compile error with line and column: 61 malformed-schema cases in the portable tests, compile-fail tests for the reflection path. |
| E10 no equality operator | A member-wise `operator==` generated by reflection. |
| E11 unknown fields | Skipped and dropped, and said so. |
| E15 "620 to 8,150 times" | Replaced by measured build cost from `.proto` to linked program, both generators (section 4). |
| E17, E18 microbenchmarks on a defective harness | Replaced by end-to-end unary calls over HTTP/2 (section 5). |
| E19, E20 interop and gRPC parity | Golden vectors from `protoc`; a real gRPC server called by a pinned grpc-go client (section 6). |
| E22 toolchain | The compiler is GCC 16, a released compiler with P2996 (section 2). |

The cover note states this delta. P5 never claims streaming, bidirectional gRPC, or a general
replacement for every `protoc` feature.

## 2. Implementation and toolchain

Component model: this repository builds its own minimal implementation of exactly the studied
features (namespace `tep`), independent of ctpb's code and of the integration library.

- Portable layers, plain C++23: proto3 front end (`schema.hpp`), wire primitives (`wire.hpp`),
  gRPC framing (`grpc.hpp`). They build with GCC 16, clang 22 and MSVC 19.51.
- Reflection layer (`reflect.hpp`): static schema tables built once per translation unit, message
  synthesis with `define_aggregate`, the codec, and endpoints that bind a handler class to a
  service. GCC 16 only today.
- Next: the HTTP/2 transport (libnghttp2, pinned), the `protoc` arm, the benchmark server with
  runtime arm selection, the schema generator, the grpc-go interop programs.

Compiler. GCC 16.2.1 (Arch package `gcc 16.2.1+r23+gd564253eb6c8-1`, the image's snapshot of
2026-09-30) defines `__cpp_impl_reflection` 202603L with `-freflection`. It is a released
compiler that anyone can obtain, which answers the brief's requirement. Bloomberg's clang-p2996
fork (ctpb's compiler) is a branch and is not used. Stock clang 22.1.8 rejects `-freflection`.
Both generators are compiled by the same GCC, so the compile curves isolate the generator.

Windows. MSVC 19.51 has neither P2996 nor `#embed`. The portable layers are tested with MSVC.
For the reflection layer Alex chose (2026-10-23) MinGW-w64 GCC 16 on the laptop's Windows for
both generators, so the same compiler runs on both OSes and the OS is the only change, after a
desktop probe that it builds and passes the reflection tests. The probe passed on 2026-10-23:
WinLibs GCC 16.2.0 (MinGW-w64 14.0.0, UCRT) builds every layer and passes all 14 tests. Linux has
GCC 16.2.1 (a branch snapshot); pinning one exact version on both OSes is decided before the
freeze.

Compiler findings so far (functional, desktop):
- GCC 16.2.1 miscompiles `std::string_view::find` from a nonzero offset when a `constexpr`
  function receives a string literal: it returns the index plus the offset, at `-O1` and `-O2`
  in the minimal reproduction and even at `-O0` in one helper. clang 22 is correct; plain C
  `memchr` and non-constexpr callers are correct. The portable layer avoids `find` in
  constexpr code. Minimal reproduction in `design/compiler-findings.md`.
- GCC 16.2.1 with `-fsanitize=null`, `nonnull-attribute` or `returns-nonnull-attribute` cannot
  constant-evaluate the reflection layer. The GCC sanitizer configuration drops those three.
- clang 22 with GCC 16's libstdc++ cannot construct `std::string` in constant evaluation; clang
  builds use libc++.

## 3. Arms

One binary with runtime arm selection for the arms this repository implements. `protoc` is a
pinned separate tool.

| Arm | Messages | Dispatch | Transport | Where |
|---|---|---|---|---|
| R (reflection) | synthesized by `tep` from the `.proto` text | synthesized route table | this repository's HTTP/2 server | the benchmark binary |
| P (protoc) | `protoc`-generated classes, libprotobuf (pinned, static, same compiler and flags) | a hand-written route table of the same shape | the same server | the same binary |
| G (gRPC C++), reference | `protoc` plus `grpc_cpp_plugin` | gRPC's callback API | gRPC's own | its own binary, documented best configuration |

R against P isolates what the generator produces: decode, encode and dispatch, on the same
transport and threads. G is the answer to "what does a C++ user get today". G costs the largest
engineering item of P5 (gRPC C++ with its dependencies, pinned, on both OSes). Alex kept G
(2026-10-23); it is built after R and P, off their critical path.

## 4. Compile curves

Generators:
- G_R: one translation unit embeds the schema, runs `define_messages`, instantiates an endpoint
  per service with a stub handler, and encodes and decodes every message once.
- G_P: `protoc` generates `.pb.h` and `.pb.cc`; the same user program, written against the
  generated API, is compiled with the `.pb.cc` and linked with libprotobuf.

Measured quantity per build: wall time and peak RSS from `.proto` to linked executable, serial
(one compile at a time), split into phases (generate, compile per translation unit, link).
libprotobuf itself is prebuilt, as users have it; its build is reported once, separately.
Release flags (`-O2`, same for both; G_R adds `-freflection`). Placement from
`lab/laptop/README.md`.

Schema generator `bench/gen_schema.py --shape S --n N`, deterministic:
- S_wide: one message with N fields cycling through the 15 scalar types and one enum, and one
  service with one rpc.
- S_many: N/8 messages of 8 fields each, every second message holding a field of the previous
  message type, and one service with one rpc per message.

Sizes: N in {16, 32, 64, 128, 256, 512, 1024, 2048, 4096}: 9 sizes x 2 shapes x 2 generators =
36 cells. The primary curve uses default compiler limits, since users do; above the largest
size that compiles under defaults, a declared secondary curve raises `-fconstexpr-ops-limit`
(value fixed in the frozen design). The largest default-limit size per shape is itself a result, once reproduced on the laptop.
Decided 2026-10-30 (`design/revision-log.md`): `many` 4096 is the one secondary-curve cell, built
with `-fconstexpr-ops-limit=67108864`.

Default-limit ceiling, desktop pass/fail probe (no timing), commit d0545b3, GCC 16.2.0: `wide`
passes 4096; `many` passes 2048 and fails 4096. GCC's limit is 33,554,432 operations per outermost
constant evaluation (GCC counts every non-constant expression node it evaluates, `constexpr.cc` in
`cxx_eval_constant_expression`, and resets the count per `cxx_eval_outermost_constant_expr`), and
the schema tables are one evaluation. A variable template first used inside another evaluation
(the tables inside `define_messages`) shares that evaluation's count; one forced earlier gets its
own. Operation counts from bisecting the limit (`bench/constexpr_ops.sh`; deterministic for one
GCC build, not a timing; engineering guidance only, reproduced on the laptop before anything cites
them) guide the engineering: the tables of `many 1024` take 9.47M operations (9.2k per field),
down from 30.0M the same morning and from 72k per field at the first commit; `-O2` and `-O0` give
the same counts within 1%. Reaching 4096 fields under default limits needs about 8k per field.
Two levers: fewer operations
(which also shortens the compile, the measured quantity) and stages evaluated separately (each
with its own limit; it raises the ceiling without shortening the compile). The laptop pilot's
`-ftime-report` shows how much of the compile constant evaluation takes, which weighs the two.
The ladder is fixed after this engineering and the pilot.

Replicates (D9): one contrast (G_R against G_P) per shape and size, m = 18, Holm at alpha 0.05:
alpha/m = 0.00278, so R = 9 suffices (2^-9 = 0.00195); take R = 10. Order interleaved
(R, P pairs, order randomized within each pair). 360 builds.

Time: no measured basis yet. T = sum over cells of 10 x t(cell). The laptop pilot measures
t(cell) for the smallest and largest cells of each generator. ctpb's retake on the laptop (a
different compiler and implementation, so only an order of magnitude) took 2 to 9 s per build
at 5 to 100 fields.

## 5. End-to-end unary calls

Server: the benchmark binary, arm R or P, threads pinned to the lab's server cores; G as its own
binary on the same cores. Cleartext HTTP/2 with prior knowledge.

Load generator: h2load (nghttp2, pinned, built from source) with a prebuilt gRPC request body,
closed loop, drives the timed runs. ghz (grpc-go based) runs the interop check and one
cross-check (Alex, 2026-10-23).

Workloads: two payloads (small: a 3-field message, as ctpb's Person; medium: about 1 KiB with
nested and repeated fields) x two loads (one connection and one stream, for latency; a saturating
number of connections and streams fixed by the pilot, for throughput). Metrics: requests per
second (headline), latency median and p99, server CPU and peak RSS.

Comparisons per OS: R against P in 4 cells, R against G in 4 cells: 8. Over both OSes m = 16;
alpha/m = 0.003125, R = 9 suffices; take R = 10, with 4 windows per replicate as in the lab's
other campaigns. Windows per OS: 3 arms x 4 cells x 10 x 4 = 480. Window length: the laptop
trials of 2026-10-22 measured 6.116 s per window on Arch and 6.123 s on Windows for closed-loop
windows (plan v2 section 3.1), and every job discards 80 s of warm-up. gRPC windows over HTTP/2
are unmeasured; the pilot measures them.

## 6. Interoperability (functional, not timed)

A pinned grpc-go client calls every rpc of the test services on the R arm and checks every
response field; the same client checks the P arm. A grpc-go server answers a `tep`-encoded
request sent by a small test client, so both directions of the wire format are exercised. The
golden vectors in `tests/golden/` are regenerated with the pinned `protoc` before any freeze.

## 7. Hypotheses (candidates only; written and frozen later)

- Compile: for each shape, the G_R build time grows at most linearly in N up to the largest
  default-limit size, and the ratio G_R / G_P per cell is reported with its BCa interval. No
  direction is pre-claimed until the pilot.
- End to end: arm R serves at least as many requests per second as arm P in each cell.
- Engineering rule (D2): R is engineered until it wins where it can; losses are reported.

## 8. Threats and declared gaps (draft of `bench/coverage.json`)

- Sanitizers on the reflection layer: no clang tool can parse it; GCC gives ASan, TSan and UBSan
  without the three null checks; MSan is not available for it. Needs Alex's yes (STATE.md).
- One reflection compiler (GCC 16). Results are tied to it; the version is part of the method.
- Synthetic schema shapes. `import`, maps, oneofs and proto3 `optional` are not supported, so no
  real-world schema with them can be measured.
- Windows depends on decision 1 in STATE.md.
- Compiler defects found during development (section 2) are reported in the paper's threats.

## 9. Decisions (Alex, 2026-10-23)

  it builds and passes the reflection tests; otherwise Windows is a declared gap.
- D-S: GCC sanitizer records for the reflection layer, the full clang set for the portable
  layers, gaps declared in `bench/coverage.json`.
- D-G: arm G is kept and built after arms R and P.
